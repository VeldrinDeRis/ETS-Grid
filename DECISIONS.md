### D-007 · Анимации — ванильный `motion`, не `motion/react` ✅
- **Дата:** 2026-10-14 · **Решил:** Дмитрий (предложил Claude)
- **Почему:** `motion/react` требует React (через `preact/compat` бандл растёт), а лимит JS жёсткий. Ванильные `animate` / `inView` работают в скриптах Astro и в островах Preact.
- **Правила:** только transform/opacity, 200–600 мс, без скроллджекинга и `scroll()`; при `prefers-reduced-motion` анимации не запускаются; без JS контент виден.

| Инструмент | Что предлагает | Почему не берём |
|---|---|---|

### D-022 · Сначала спецификация, потом утверждение, потом код ✅
- **Дата:** 2026-10-14 · **Решил:** Дмитрий (предложил формат Claude)
- **Что:** каждый модуль сайта сначала описывается в `specs/SPEC-0NN-*.md` по шаблону `specs/_TEMPLATE.md`. Статусы: Черновик → Утверждена → В работе → Готово. Код модуля пишется только после утверждения; коммиты ссылаются на спецификацию (`SPEC-002: …`). Поведение меняется сначала в спецификации (с записью в «Ревизии»), потом в коде. «Готово» — когда отмечены все критерии приёмки.
- **Кто утверждает:** спецификации фундамента, каталога, карточки, подборщиков, корзины и главной — Дмитрий. Мелкие (SEO и разметка, контентные страницы, служебные) Claude утверждает сам и записывает это в журнал.
- **Содержание спецификации:** не пересказ ТЗ, а ссылки на его разделы плюс то, чего в ТЗ нет: контракт (данные, URL, интерфейс), поведение и состояния, доступность, «Мокап → боевой» (что заглушено и какой стык нужен потом; неизвестное — вопросом, не выдумкой), критерии приёмки `AC-NN`, зависимости, что не входит.
- **Почему:** мокап должен перерасти в боевой сайт без переписывания (D-019), поэтому «что строим» фиксируется отдельно от «как в мокапе». Утверждённые контракты позволяют вести модули параллельно (агенты в отдельных git worktree) без расхождений при слиянии.
- **Порядок:** SPEC-001 «Фундамент» (адреса, схема данных, раскладка, шапка и подвал, имена токенов) делается первым и последовательно, он блокирует остальные. Остальные модули можно вести параллельно.
- **Связь с журналом:** DECISIONS — «почему», specs — «что именно». Решение, принятое по ходу спецификации, всё равно записывается сюда.

### D-023 · Библиотека тестов: критерии приёмки становятся тестами ✅ (уточнено D-024)
- **Дата:** 2026-10-14 · **Решил:** Дмитрий (предложил формат Claude)
- **Что:** тесты в `ets-grid-site/tests/` (по инструкции 02), индекс покрытия — `ets-grid-site/tests/README.md` (критерий → тест → статус). Уровни:
  - `unit/` — Vitest: формулы подборщиков и Carport, логика фильтров, корзина, форматирование;
  - `data/` — Vitest + Zod: каталог соответствует схеме, все ссылки (`cross_level`, составы пакетов) ведут на существующие товары, у каждого листинга есть товары или экран «підберемо»;
  - `e2e/` — Playwright на 375 и 1440: сценарии ТЗ §7, проверка без JS (каталог и цены в HTML), доступность через axe-core; визуальные эталоны — только после утверждения дизайна.
  - Lighthouse — через MCP Chrome DevTools, отчёты в `qa/`, в библиотеку не входит.
- **Правила:** (1) номер критерия `SPEC-0NN/AC-NN` стоит в названии теста, `--grep SPEC-0NN` гоняет модуль; (2) для логики тест пишется до кода по примерам из спецификации; (3) для интерфейса — вместе с кодом, до статуса «Готово»; (4) найденный баг — сначала воспроизводящий тест, потом исправление; (5) перед слиянием параллельной ветки в `main` проходят все тесты, а не только свои; (6) фикстуры отдельно от `catalog.json`, чтобы замена демо-каталога не ломала тесты формул.
- **Почему:** параллельная ветка считается готовой по зелёным тестам, а не по «вроде работает»; тесты логики — исполняемый контракт между ветками.
- **Пакеты** (Vitest, `@playwright/test`, `@axe-core/playwright`) ставятся в рамках SPEC-001, версии сверяются через Context7 (Vitest должен работать с Vite 8 из Astro 7).

### D-024 · Структура тестов по тому, что проверяем; уточняет D-023 ✅
- **Дата:** 2026-10-14 · **Решил:** Дмитрий (предложил Claude)
- **Что:** вместо трёх папок D-023 (`unit/`, `data/`, `e2e/`) — шесть категорий в `ets-grid-site/tests/`:
  - `unit/` — Vitest: формулы, фильтры, корзина, форматирование цен и единиц;
  - `data/` — Vitest + Zod: схема каталога, целостность ссылок, у каждого листинга есть выдача или «підберемо»;
  - `build/` — Vitest, разбор HTML из `dist/` без браузера: все адреса карты URL собраны; товары, цены, FAQ в HTML без JS; title, description, canonical, JSON-LD; нет битых внутренних ссылок; бюджет JS ≤ 100/150 КБ gz; ≤ 2 файлов шрифтов на первом экране; нет `#C8F03C` и Unbounded; украинская типографика (`кВт·год`, неразрывные пробелы);
  - `functional/` — Playwright на 375 и 1440: фильтры и URL, «з монтажем», корзина, оформление, подборщики;
  - `a11y/` — Playwright + axe-core: каждый шаблон в палитрах А и Б, проход с клавиатуры, шторка (фокус, Esc), reduced-motion;
  - `visual/` — скриншоты-эталоны: шаблоны × 375/1440 × палитра, ключевые компоненты в состояниях;
  - плюс `fixtures/` (данные отдельно от `catalog.json`) и `helpers/` (экраны, переключатель палитры, объекты страниц).
- **Пороги:** unit и data блокируют каждый коммит; build, functional, a11y блокируют слияние в `main`; visual до утверждения дизайна только отчёт, после — блокирует слияние.
- **Команды:** `npm test` (unit + data), `test:build`, `test:functional`, `test:a11y`, `test:visual`, `test:smoke` (метка `@smoke`, главный сценарий), `test:all` (перед слиянием).
- **Связь со спецификациями:** один критерий может проверяться в нескольких категориях; индекс `tests/README.md` указывает категорию и файл. Тесты модуля — в своих файлах (`functional/catalog.spec.ts`), общее — в `helpers/`, чтобы параллельные ветки не конфликтовали.
- **Вне библиотеки:** Lighthouse через MCP и скриншоты для заказчика — в `qa/`, это отчёты.
- **Почему:** у каждой категории свой вопрос, скорость и порог; `build/` — самая дешёвая проверка самых жёстких правил ТЗ (HTML без JS, SEO, бюджеты, запрещённая эстетика) так, как сайт видит поисковик.
- **Оговорка:** визуальные эталоны снимаются на Windows; при переходе на CI под Linux — переснять там.
